### Week 1 — Data Ingestion & Index Computation Engine

**Objective:** A service that pulls real, live Polymarket data and produces correct, liquidity-filtered, VWAP'd index prices — with historical storage.

**Build prompt for your agentic coder:**
> Build the `data-ingestion` service (package `xleuth_ingestion`) in Python 3.12 for Xleuth, a prediction-market index platform. Requirements:
> 1. Connect to Polymarket's public Gamma API, CLOB API, and Data API. Specifically:
>    - Use Gamma **`GET /markets`** (not `/events`) for market discovery — `/events` nests markets inside event objects and will silently undercount your basket if parsed as flat data. `/markets` returns one flat object per market with `conditionId`, `outcomes`, `clobTokenIds`, `volume24hr`, a cached total-volume field, `active`, `closed`, and a nested parent-event reference. Required query params: `active=true`, `closed=false`, `order=volume24hr`, `ascending=false`, with real pagination (`limit`/`offset`) — do not assume one unpaginated call returns the full universe.
>    - Use CLOB's public read endpoints (`GET /price`, `/midpoint`, `/book`) — keyed by `clobTokenIds` from the Gamma response — for live tick price. These are unauthenticated; do not provision or wire in any CLOB API key/wallet-signing setup, that's only needed for order placement, not reading.
>    - Use Data API **`GET /live-volume?id={eventId}`** for live (non-cached) volume. This endpoint is event-scoped, not market-scoped — `id` must be the market's parent event's numeric ID, not a condition ID or slug.
>    - Reference https://docs.polymarket.com for exact response schemas — do not guess field names, fetch and inspect real responses first.
> 2. Implement a liquidity filter that excludes any market below a configurable volume/open-interest threshold (read from `.env`, e.g. `MIN_MARKET_VOLUME_USD`, `MIN_MARKET_LIQUIDITY_SCORE`). This filter must run before any VWAP computation.
> 3. Build `event_map.py`: from the Gamma `/markets` pull, map each basket market to its parent `eventId`, collapse to the set of *unique* event IDs (some basket markets share a parent event, some don't), then call `/live-volume` once per unique event ID — never once per market, since that would double-count volume for markets sharing an event. Match the response's `markets[].market` (condition ID) back to each basket entry to attach live per-market volume.
> 4. For markets with multiple sub-outcomes (e.g. "What price will BTC hit in July?" with $40k/$65k/etc. outcomes), compute a single VWAP across the sub-outcomes, using CLOB-sourced live prices, to produce one representative price for that market.
> 5. Implement basket construction: given a theme/window definition (e.g. `TOP50-JULY` = top 50 non-sport markets by volume resolving in July), compute the basket's VWAP index price from its filtered, single-priced constituent markets.
> 6. Persist every computed index price point and every constituent market's filtered price to PostgreSQL using TimescaleDB hypertables. Schema must include: `timestamp`, `basket_id`, `index_price`, and a constituent breakdown as JSONB containing per-market `conditionId`, `clobTokenId`, `eventId`, live CLOB-derived price, and live Data-API-derived volume. `eventId` must be stored per constituent (not just at basket level) so downstream consumers can re-derive the event-dedup grouping without re-fetching Gamma.
> 7. Write a polling loop (configurable interval via `.env`, e.g. `INGESTION_POLL_INTERVAL_SECONDS`) that keeps this data fresh.
> 8. All thresholds, poll intervals, and API base URLs must come from `.env` — none hardcoded.
> 9. Write integration tests that hit the real Polymarket API (not mocks) and assert the pipeline produces sane, non-empty output for at least 2 real, currently-active markets. Do not fabricate sample data anywhere in tests or seed scripts.
> Do not build the backend API, matching engine, or contracts in this task — only data ingestion and index computation.

**Verification prompt:**
> Run the data-ingestion test suite and show me the raw output. Then, independently query the Polymarket Gamma `/markets`, CLOB `/price`, and Data API `/live-volume` endpoints directly (print the raw JSON) for one market that was included in a basket, and manually recompute its VWAP by hand from that raw JSON. Confirm the number matches what the pipeline stored in the database, to the cent. Show me the actual liquidity filter excluding at least one real low-volume market by printing which markets were excluded and why. Additionally: print the raw CLOB response for one market's live price and confirm it differs from that same market's cached Gamma `outcomePrices` value at the same moment (proving the pipeline is actually using CLOB, not silently falling back to Gamma's field). Then find one event in the basket that contains more than one constituent market, print the `/live-volume` response for that event's ID, and show the dedup logic assigning the correct per-market `value` to each of those constituents without a duplicate API call. Do not tell me it passed — show me the numbers.
